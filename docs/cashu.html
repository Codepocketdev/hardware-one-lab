Spending Cashu ecash with a hardware key: a lab experiment

By Codepocketdev, Nairobi. 22 November 2026, tests run on 20 and 22 November 2026. Main write-up · Source code on GitHub

Tested on a Trezor Model One. Independent research, not affiliated with SatoshiLabs or Trezor.

I added a third mode to my patched Trezor Model One. It signs the spend of Cashu ecash that is locked to its key: the device checks the lock, shows the raw secret page by page, and signs only after a button press. Mints accepted the signature: a local test mint, and once a real mint, where an 8 sat token created in Minibits was spent on mint.minibits.cash.

This is a lab experiment. Do not use it with real funds.

  • Everything except one test ran on a local test mint with fake funds. That one test spent a single 8 sat token on a real mint (mint.minibits.cash) on 22 November 2026.
  • The firmware is unofficial, unsigned and unaudited. The lab device’s recovery words were exposed during the work, so its keys are public. The real-mint test used a freshly generated seed instead.
  • Use a spare device and throwaway keys only.

How a locked proof is spent

Cashu ecash is made of proofs, and each proof carries a secret. NUT-11 lets a sender lock a proof to a public key. The secret becomes a short JSON text naming the key, and the mint refuses to swap the proof unless the spender attaches a valid signature. That signature is a BIP-340 Schnorr signature over the SHA-256 hash of the secret string, the same primitive the device already uses for Nostr. The mint compares keys by x-coordinate only, so the device’s x-only key works as a lock key with a 02 prefix.

What the device does

  • Key: m/44'/1237'/2'/0/0, a separate path from the Nostr key, so ecash and a Nostr identity are not linked.
  • Commands travel inside the normal Ping message: CASHUPUB returns the x-only key, and CASHUSIG BEGIN, ADD and SIGN transfer a secret and return the signature after approval.
  • It signs only a P2PK secret with exactly one data field whose lock key is its own, written as 02 or 03 plus its x-only key. The secret must be printable ASCII, at most 600 bytes, with no backslashes. Anything else is refused and nothing is signed.
  • Review: a summary page (“Cashu P2PK lock”, “Lock key is ours”, the length), then the raw secret at 80 characters per page, ending with a Sign button. The left button cancels at any point.
  • Home screen: the right button now cycles the clock, the Nostr signer panel and the Cashu signer panel, which reads “Ready”.

What was tested

  • On the device, a test script passed 9 of 9 checks: the Cashu key differs from the Nostr key, signatures over the SHA-256 of the secret verify for compact and spaced JSON, and five bad inputs were refused (locked to another key, not P2PK, a backslash, non-ASCII text, two data fields).
  • On a local Nutshell 0.18.2 mint with a fake Lightning backend, which reports NUT-11 as supported, ecash locked to the device key was refused without a signature. It was then redeemed with a signature made on the device. A software stand-in signer was used first to check the flow before the device replaced it.
  • With cashu.me, a token locked to the device key was created: four proofs with compact secrets and empty tags. Each was signed on the device, one review round per proof, and the local test mint paid out 14 sat.
  • On a real mint, on 22 November 2026: an 8 sat cashuB token, created in Minibits and locked to the device key, was spent on mint.minibits.cash. The device showed “Lock key is ours” and the 171-character secret over 3 pages, and signed on the last page. The mint accepted the signature with no fee, and the new proofs were received in cashu.me. A host tool, not a wallet, built and sent the swap.
  • A second test script, tools/cashu_negative_test.py, ran 28 checks on the device and all passed. Twenty-one automatic checks were each refused with the firmware’s own message before any button prompt: wrong command order, bad lengths, a wrong or truncated lock key, a 04 key prefix, not P2PK, a missing closing bracket, two or no data fields, a backslash, non-ASCII text, a control character, and a wipe of the loaded secret after a refusal. With button presses, cancelling on the first page and on the last page both produced no signature, and a bare SIGN afterwards was refused. An approved signature verified for the secret and failed for an altered secret and for another key.
  • 2-of-2 on a local Nutshell 0.18.2 test mint with a fake Lightning backend (tools/cashu_2of2_test.py): an 8 sat token was locked to the device key as data plus a software key in the pubkeys tag, with n_sigs 2. The device showed the 266-character secret over 4 pages and signed on the last. The mint refused a device signature alone, a software signature alone, the device plus a wrong second key, and the same signature twice. It accepted the device plus software signatures, then refused a replay of the spent proof. Result: 6 passed, 0 failed.
  • 2-of-2 with cashu.me (tools/cashu_2of2_cashume.py): an 8 sat token was minted on the local test mint, locked to the device key as data plus a throwaway cashu.me public key in the pubkeys tag, with n_sigs 2. The device signed once on the script’s request and the mint refused that signature alone. cashu.me recognised the token as locked to its key, but Receive failed with the mint’s message: not enough pubkeys (2) or signatures (1) present for n_sigs (2). The device was not asked to sign during that attempt.
  • 2-of-2 spent with cashu.me and the device, through a local bridge (tools/cashu_bridge.py): the bridge sat between cashu.me and the local test mint. When cashu.me sent its swap with one signature on the locked proof, the bridge asked the device to sign the same secret, the device showed the 4 pages and signed after a button press, and the bridge added that signature to the witness. The mint accepted both signatures and cashu.me received 7 sat (8 sat minus a 1 sat fee).
  • On the home screen of the real device, the right button cycled the clock, the Nostr signer panel and the Cashu signer panel.

Not tested

  • Spending beyond one proof on a real mint. Only a single 8 sat proof on Minibits was spent; other mints, larger tokens and several proofs on a real mint were not tested.
  • The SIG_ALL flag, wallets other than cashu.me, and Nostr zaps with ecash.
  • Whether a lock really lapses after its locktime when no refund key is set.
  • Multisig beyond that one local test. The second key was a software key, the device key had to be the data key, and the firmware does not read n_sigs, so only the on-screen secret shows that two signatures are needed. 2-of-3, the refund path and a real mint were not tested.
  • The bridge is a stand-in for a wallet hook. cashu.me never asked the device for anything; a small program on the same PC did. With SIG_INPUTS the signatures do not cover the swap’s outputs, and the device shows only the secret, so a malicious bridge or PC could send the money elsewhere after the button press. The bridge signs any input locked to the device key plus another key with n_sigs of 2 or more, and it was tested on a local test mint with one wallet and one proof.
  • Any wallet asking the device to sign. In every test a separate script requested the signatures, not the wallet.

Limits

  • With SIG_INPUTS only the secret is signed, so the device cannot show an amount or a recipient. It shows the raw secret with the lock key and any tags, and the signature acts as a bearer approval for that proof.
  • Each proof needs its own approval, so a token with four proofs took four rounds of button presses.
  • Newer mints use 33-byte keyset IDs (starting with 01), while a cashuB token carries only the first 8 bytes. The host tool has to look up the full ID in the mint’s keyset list before any request, or the mint refuses it.
  • Redeeming swaps the locked proof for new unlocked proofs, so the result is a plain bearer token until a wallet imports it. The host tool does the swap, not a wallet, and it does not verify the mint’s DLEQ proofs.
  • I found no Cashu wallet that can ask an external device to sign. Nostr’s signer protocols do not carry arbitrary signing requests either, so a wallet-side hook is still missing.
  • The mint must support NUT-11. A mint that does not may treat locked ecash as spendable by anyone.
  • The Nutshell command line adds a one-day locktime to locks by default. The tests turned that off with LOCKTIME_DELTA_SECONDS=0.

Try it

The CASHU.md file in the repository has the design and test notes. In short, apply patches 01 to 04 from the patches folder, in order, with git apply, build and flash a spare device, then run:

python tools/cashu_device_test.py

The mint tests are tools/cashu_mint_test.py, tools/cashu_import_token.py and tools/cashu_sign_secrets.py. The mint test refuses any mint that is not local unless you override it. tools/cashu_sign.py decodes cashuA and cashuB tokens (show) and redeems a locked token on a mint (redeem is a dry run unless --send is added); unlike the mint test, it does not refuse real mints. tools/cashu_negative_test.py runs the refusal and cancel tests.
